# 1.1 Starting a process from a program on disk

## What happens

When a user requests execution, the shell calls `fork()` to create a child process, and the child calls `execve()` with the path to the executable. This traps the CPU into kernel mode (via the `syscall` instruction) so the kernel can perform privileged operations. The kernel verifies the executable's format (typically ELF on Linux, failing with `ENOEXEC` otherwise), destroys the old address space, and builds a new one: a fresh page table is created, and the ELF program headers describe how the segments (`.text`, `.data`, `.bss`) should be mapped - lazily via demand paging, so pages are only read from disk when first accessed. The dynamic linker (`ld-linux.so`) is mapped in to resolve shared libraries like `libc.so` at runtime, the user stack is set up with `argc`, `argv[]`, `envp[]`, and the auxiliary vector, and the program counter is initialized to the ELF entry point (`_start`, which eventually calls `main()`). The process is then placed on the ready queue, and when the scheduler dispatches it, the kernel executes a privileged return instruction (`iret` on x86-64, `eret` on ARM) that restores the saved user context and switches the CPU to user mode, and the program starts running.


## Why the kernel -> user mode switch is necessary

The switch from kernel mode to user mode is necessary because the CPU has two privilege levels (on x86-64: ring 0 = kernel, ring 3 = user). In kernel mode all instructions are allowed, including privileged ones - direct hardware access, I/O, manipulating page tables (`CR3`), and changing the privilege level itself - while in user mode privileged instructions are forbidden and any attempt raises a general protection fault. If user programs could execute privileged instructions, a program could set the page-table base register itself and read or write the memory of other processes or the kernel, breaking process isolation; the only way for a user program to do anything privileged would no longer be through system calls, where the kernel validates every request against permissions (UIDs, file permissions, capabilities). Running the process in user mode therefore guarantees the kernel remains in control of all shared resources, and confines a buggy or malicious program so it can only crash itself (e.g. segfault), not the operating system or other processes. In short: the kernel sets everything up in kernel mode, then hands control to the program in user mode so it runs with restricted privileges while the Linux kernel retains full control of the machine.
